# Codehawk improvement and verification strategy

Codehawk produces candidate findings, ranks files for human or agent review, then builds reports from reviewed findings. Measure each stage individually. A faster scan can still cost the reviewer more time if it produces more noise.

| Priority | Improvement experiment | Check and decision |
| --- | --- | --- |
| 1 | Establish a repeatable baseline before tuning. Use fixed local Git snapshots covering a small repository, a many-file repository, and a one-file change with many disjoint hunks. Run repo and commit modes separately. | Compare baseline and proposed change on the same machine and Node version with identical inputs and dependency lookup settings. Alternate run order for seven paired runs. Record median wall time by stage, peak resident memory, worksheet bytes, candidate count, unreadable files and truncation. Retain raw observations. |
| 2 | Extend the existing planted-issue fixture with independently labeled benign and problematic cases. Include changed and unchanged lines and a clean repository. Keep a held-out set for evaluating rule and ranking changes. | Match expectations by file, rule family and line range. Count missed expected cases and unexpected candidates separately. Report candidate recall, false positives per 1,000 reviewed lines, and the fraction of labeled files in the read list. Review every lost match before release. |
| 3 | Profile snapshot reads and changed-line selection. In the current implementation a snapshot cache miss reads via Git, and the scan tests each line against changed ranges. Measure both before selecting an optimization. | If Git startup dominates, trial batched reads. If range checks dominate, trial an advancing cursor over sorted merged ranges. Compare candidate locations, ordering, read list, unreadable counts and truncation against the baseline. Keep a change only if its speedup exceeds measured run-to-run variation without losing expected coverage. |
| 4 | Measure reviewer workload through the full command path. Independently review a fixed sample of generated findings for accurate location, actionable evidence, and agreement with the labeled outcome. | Record reviewer minutes per confirmed finding and sample size. Compare with recall and clean-case noise. Check that the same finding identity, location and resolution state agree across JSON, Markdown, HTML and SARIF, accounting for resolved findings intentionally omitted from SARIF. |

## Check cadence

Run `npm test` on each proposed change. The existing suite exercises scope selection, report building, fix approval, resolution and dependency lookup. Use its temporary repositories and mocked dependency responses as starting points for deterministic comparisons. For scanner or ranking changes, compare the held-out cases and paired timing runs before accepting the change. For release candidates, repeat on the declared minimum Node version (18) and the team's primary runtime. Archive the commits, fixture revision, environment, raw measurements and reasons for accepting any tradeoff.

The first benchmark run establishes the baseline. The proposed comparisons do not imply a measured speedup or a current precision score.
